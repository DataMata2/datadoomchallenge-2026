# Task 5 integration handoff

Assistant, draft reports and independent metrics are implemented. The full backend suite passes 244 tests. Real provider smoke is pending the parent's resolution of the recorded automatic-review rejection; no Task 5 model call has yet been sent. Updated generated OpenAPI and fictional examples publish all implemented request/response shapes.

- `POST /api/assistant {content, report_id?}` and `POST /api/reports/{id}/messages {content}` return `AssistantResponse`: explicit status `ok|clarification|error`, stable report_id, structured **message object**, spec/output, nullable **metric_run_id**, nullable strict action/error. These names supersede Task 4's planned assistant example. The message content contains backend-computed numbers; action explanation is intent only. Poll the report/run for custom assessment progress.
- Reports add status `draft|ready`. Draft spec/output are both null and stale=false; refresh/metric creation reject drafts. Ready retains both values. Legacy populated reports load as ready without a migration write. First request persists draft/user message before translation. Clarification/provider errors retain saved output/context. Store at most 40 messages; translate the last 12. Requests accept nonblank content up to 8,000 characters.
- The internal native JSON action always has operation, explanation, patch, definition, metric_id and question. Only one operation payload is nonnull. An analysis patch is a complete valid target plus a unique explicit field mask. Only allowed masked paths update existing context; null/default wire fields elsewhere never erase prior dates/channel. Whole hours/cohorts/lists replace. Invalid keys/IDs/merged bounds fail before analytics/job execution. No generated code, SQL, URL fetch or tool execution exists.
- Custom definitions include required nullable na_condition. Boolean domains are strict false/true; numeric domains are finite nonnegative discrete steps. Baseline/reserved/report-local IDs reject. Definitions remain immutable. New definitions POST directly as `/api/reports/{id}/metrics` bodies. Reruns use `/api/reports/{id}/metrics/{metric_id}/runs` with no body, or assistant `rerun_metric`. Concurrent duplicate runs/duplicate definition IDs return 409; missing resources 404; invalid/draft/empty selections 422.
- The single existing JobManager owns startup/recovery/close and both evaluation/custom handlers. Custom registration atomically persists run, definition snapshot, saved root selection/provenance and report entry, then dispatches outside the transaction. Custom run checklist fields/evaluation_id are null and item assessment_id is separate. Runs add optional report_id/metric_snapshot/selection_spec/selection_generated_at; legacy evaluation runs remain readable. Existing run and cancel endpoints handle both kinds.
- `GET /api/reports/{id}` returns typed custom definitions, run_ids/latest_run_id, full run history, current projected results, aggregate/groups and out_of_scope_count. Results are separate `custom_assessments` documents accessible at `/api/custom-assessments/{id}`; source_url retains dataset/source ID, and judgment evidence_turns index the complete original transcript. Prompt/model/usage-attempt identity is retained separately. No baseline source/evaluation/score/export is modified.
- Aggregates explicitly expose selected, assessed, applicable sample, N/A, failed, pending, cancelled, interrupted and uncovered counts plus distributions. Boolean values are true-percent; numeric values are raw-scale means. Latest explicit run targeting each dataset/source wins, including pending/failure; history remains. Compatible saved selections reuse results; changed datasets cannot reuse matching source IDs. Updated root/groups project by intersection; uncovered/out-of-scope remain visible and filters never silently rerun a model. False for client-led contact describes ownership and is not a negative quality grade.
- Spec/output updates use one atomic callback with an expected-spec guard and retain concurrent messages/metric registration. Refresh preserves existing custom history/coverage. Custom workers modify only run/result collections, so progress cannot overwrite report changes. Startup reconciles result/item gaps, retains completed paid work and unknown reservations, and interrupts unsent work without retry.
